# 抓包与 HTTPS 解密方案（草案）

状态：可行性分析，尚未纳入版本计划。目标效果：查看最近请求，并可对指定主机做 HTTPS 解密（MitM）。

## 1. 结论

| 能力 | 可行性 | 依赖 | 工作量 |
| --- | --- | --- | --- |
| **连接级记录**：域名、进程、规则、节点、流量、时长 | 可直接做 | Mihomo `/connections` 已提供（含 SNI 嗅探、进程名） | 小，即现有「连接」页加「已关闭记录」和导出 |
| **HTTP 明文抓包**：方法、URL、头、正文 | 可做 | 澜流自建 HTTP 代理层 | 中 |
| **HTTPS 解密（MitM）** | 可做，有限制 | 自建代理层 + 本机根证书 | 大，约等于 v0.1 的总工作量 |

Mihomo 本身不支持 MitM（已检查源码 `MetaCubeX/mihomo@3f27ef3`），因此解密层必须由澜流用 Go 自己实现。Go 标准库的 `net/http`、`crypto/tls`、`crypto/x509` 足以实现，可参考 `elazarl/goproxy`（BSD 许可）的 MitM 实现。

## 2. 架构

只在开启抓包时插入解密层；关闭时链路与现在完全相同。

```text
抓包关闭： 应用 ──系统代理──▶ Mihomo :7890 ──▶ 节点

抓包开启： 应用 ──系统代理──▶ 澜流 Capture :7891 ──▶ Mihomo :7890 ──▶ 节点
                                 │
                                 ├─ 主机名在 MitM 列表中：TLS 终止 → 记录请求/响应 → 重新加密发往上游
                                 └─ 不在列表中：CONNECT 原样转发，只记录主机名和流量
```

- **为什么放在 Mihomo 前面**：解密层看到的是应用发出的原始请求，Mihomo 的分流规则保持不变。
- **代价**：开启期间所有走系统代理的流量都会经过澜流进程。Mihomo 看到的来源进程会变成澜流，因此进程名由解密层自己获取：macOS 用 `proc_pidinfo` 按端口查找，Windows 用 `GetExtendedTcpTable`。
- **上游**：解密层通过 Mihomo 的混合端口转发，不另开出口。

### 新增模块

| 目录 | 职责 |
| --- | --- |
| `internal/capture/proxy` | HTTP/CONNECT 代理、TLS 终止、HTTP/1.1 与 HTTP/2、WebSocket 透传 |
| `internal/capture/ca` | 生成根证书、按域名签发并缓存叶子证书、安装与卸载信任 |
| `internal/capture/store` | 内存环形缓冲：默认 2000 条请求，单个正文上限 1 MB，总量上限 200 MB |
| `internal/capture/export` | 导出 HAR、复制为 cURL |

## 3. 根证书

| 项 | 做法 |
| --- | --- |
| 生成 | 每台机器独立生成 ECDSA P-256 根证书，名称如「Lanflow Local CA (主机名)」，有效期 2 年 |
| 私钥保存 | macOS 存入钥匙串，Windows 用 DPAPI 加密；绝不导出，也不写入日志 |
| 安装信任 | macOS 调用 `security add-trusted-cert`（弹出系统授权窗口）；Windows 导入当前用户的「受信任的根证书颁发机构」（系统会弹窗确认） |
| 卸载 | 设置中提供「移除根证书」，同时删除私钥；卸载应用时提示移除 |
| 叶子证书 | 按 SNI 即时签发，有效期 7 天以内，在内存中缓存 |

## 4. 限制（需要在界面上写明）

- **证书固定的应用无法解密**：银行、部分 Apple/Google 服务、多数聊天应用。处理方式是：握手失败时自动把该主机加入「跳过」列表并标记出来，不让应用断网。
- **不走系统代理的流量抓不到**：命令行工具和部分应用需要 TUN 模式。TUN 模式下的抓包放到更后面，做法是让 Mihomo 把匹配的流量转给解密层。
- **HTTP/3（QUIC）**：浏览器通过代理时一般不会使用 QUIC，问题不大；TUN 模式下需要拦截 UDP 443，迫使连接回落到 TCP。
- **Firefox** 默认使用自己的证书库，需要开启 `security.enterprise_roots.enabled`，界面中提供说明。
- **只解密列表中的主机**：需要逐个添加主机名，不提供「全部解密」的默认选项。

## 5. 安全与合规

- 默认关闭；每次开启时侧边栏状态条显示醒目的「抓包中」标识。
- 预置不解密列表：银行与支付、系统更新、密码管理器等域名，用户可以修改。
- 抓包数据只保存在内存中，退出即清空；导出 HAR 时默认把 `Authorization`、`Cookie`、`Set-Cookie` 打码，需要用户主动勾选才导出原值。
- 只用于分析本机自己的流量。文档和首次开启时的说明中明确这一点。

## 7. 建议排期

```text
v0.2  连接页增加「已关闭记录」和导出：零风险，覆盖「看看流量去哪了」的需求
v0.4  HTTP 明文 + HTTPS 解密（系统代理模式）
v0.5  TUN 模式下的解密
```

放在 TUN 之后的原因：解密层和 TUN 都会改变流量路径，先把基础代理做稳，排查问题时更容易定位。
