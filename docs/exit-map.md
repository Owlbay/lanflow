# 出口识别与全球流量地图（草案）

基于 Mihomo 内核的接口（`/connections` 的链路信息、`listeners` 的独立监听端口）与 Cloudflare trace 设计，全部数据表与实现均为本项目独立编写。

## 1. 思路

### 出口识别（两种来源）

| 来源 | 做法 | 准确性 |
| --- | --- | --- |
| **按节点名猜测** | 解析「🇭🇰 香港 03 IPLC」「JP-Tokyo-02」「美国 圣何塞」：国旗 emoji → 国家；中文地名按子串匹配；英文名和国家代码按完整单词匹配（避免「IPLC」被认成 PL）；城市优先于国家；「上海-东京」这类中转线路中，中国大陆通常是入口，因此排在最后考虑 | 离线、即时，但节点名可能写错或故意不写 |
| **实测** | 在 Mihomo 中额外开一个只供探测用的监听端口，绑定专用的选择组；把该组切换到目标节点后，经此端口请求 `https://www.cloudflare.com/cdn-cgi/trace`，得到出口 IP、国家（`loc`）和 Cloudflare 机房代码（`colo`，IATA 机场代码 → 城市） | 准确反映真实出口；结果缓存 24 小时，每次只探测一个节点 |

用户自己的位置：用同样的方式经 `DIRECT` 请求一次 trace 得到。

关键点：**探测走独立监听端口和独立选择组，不改变用户当前选择的节点，也不影响正在进行的连接。** Mihomo 的 `listeners` 配置支持为某个监听端口指定 `proxy`，因此可以这样实现。

### 地图

- 等距圆柱投影；视野自动缩放到所有已知地点，经度以用户位置为中心展开，使弧线走最短方向。
- 陆地用 1°×1° 网格的点阵绘制（数据由 Natural Earth 1:110m 生成，约 8 KB 的位图常量），没有图片或瓦片，离线即可显示。
- 从「你」到每条路由的出口画一条弧线：流量越大线越粗，并有光点沿线移动；切换节点时弧线平滑移到新城市。
- 右侧列出各出口卡片：节点、用途、城市、「实测」标签、延迟。

## 2. 澜流能不能做

**能做，而且难度适中。** 所需条件都已具备：

| 需要 | 来源 |
| --- | --- |
| 每个连接经过哪个代理组、哪个节点 | Mihomo `/connections` 的 `chains` 字段 |
| 每条链路的实时流量 | 对连接按出口节点汇总 `upload/download` 的增量 |
| 节点出口位置 | 节点名解析 + Cloudflare trace 实测 |
| 绘制 | MyGo 的 `chart` 和绘图 API（路径、渐变、动画） |
| 陆地数据 | Natural Earth（公有领域，可自由使用） |

## 3. 澜流的实现方案

### 3.1 模块

| 目录 | 职责 |
| --- | --- |
| `internal/geo` | 国家/城市表（代码、中英文名、别名、经纬度）、节点名解析、IATA 机场代码 → 城市 |
| `internal/locate` | 探测：探测端口 + 探测组 → 请求 trace → 解析 → 缓存（JSON，24 小时） |
| `internal/view/exitmap` | 投影、点阵陆地、弧线和动画 |
| `tools/landgrid` | 从 Natural Earth 生成陆地位图常量（开发时运行） |

数据来源全部自己整理：城市坐标使用 GeoNames（CC BY 4.0，需要注明出处）或手工整理常见的约 150 个城市；机场代码 → 城市使用 OurAirports（公有领域）。

### 3.2 运行时配置中增加的托管字段

```yaml
listeners:
  - name: lanflow-probe
    type: http
    listen: 127.0.0.1
    port: 0        # 启动时由澜流分配空闲端口
    proxy: LANFLOW-PROBE
proxy-groups:
  - name: LANFLOW-PROBE
    type: select
    proxies: [DIRECT, ...全部节点]
```

这两项属于应用托管字段，不写入订阅原文；界面中隐藏 `LANFLOW-PROBE` 组。

### 3.3 识别策略

1. 先按节点名解析，立即显示，标记为「推测」。
2. 用户点击「实测」，或节点被选为出口时，后台探测一次，成功后改为「实测」并缓存 24 小时。
3. 实测的 IP 与名称推测的国家不一致时，以实测为准，并显示提示（例如「名称为日本，实际出口为香港」），这对识别名不副实的节点很有用。

### 3.4 隐私

- 实测会经由节点访问 Cloudflare，请求本身不包含用户数据，但仍属于对第三方的请求：在设置中提供开关「实测节点出口位置」，默认开启，并在说明中写明访问的地址。
- 只做按需和单次探测，不在后台对全部节点批量扫描。

## 4. 「全球流量图」可以做到哪一步

| 层次 | 内容 | 可行性 |
| --- | --- | --- |
| A. 你 → 出口 | 每个出口一条弧线，粗细表示流量 | 可做，推荐作为第一版 |
| B. 出口 → 目标国家 | 用 Mihomo 自带的 GeoIP 国家库，把目标 IP 归入国家，从出口再画一段到目标国家 | 可做；Mihomo 的 GeoIP 库只到国家级别，弧线终点为该国的代表城市 |
| C. 精确到目标城市 | 需要城市级 IP 库（如 DB-IP City Lite，CC BY 4.0，体积超过 100 MB） | 不建议，体积太大，收益有限 |
| D. 点击弧线查看连接 | 点击弧线或出口卡片，筛选出走这条线路的连接 | 可做，与「连接」页联动 |

## 4A. 中转检测：落地在美国，中间有没有跳转

### 能看到什么

```text
你 ──① 你→入口──▶ 入口服务器 ──② 机场内部线路──▶ 落地服务器 ──③──▶ 目标网站
     可完整检测        可识别         只能推断「有没有」        可识别       看不到
```

| 段 | 能否检测 | 方法 |
| --- | --- | --- |
| **入口位置** | 能 | 连接信息中的 `remoteDestination` 是内核实际连接的节点服务器 IP；没有连接时，用配置里的 `server` 字段经 `/dns/query` 按内核的 DNS 设置解析。再用 GeoIP 查出国家，用 ASN 库查出运营商（Mihomo 已支持 ASN 数据库） |
| **你→入口的线路** | 能（P2） | 对入口 IP 执行一次系统自带的 `traceroute` / `tracert`，按路由器所属网段识别线路，例如 59.43.x.x 为 CN2；也可得到你到入口的往返时间 |
| **客户端链式代理** | 完全可见 | 配置中的 `relay` 组和 `dialer-proxy` 字段，以及连接信息中的 `chains`，都能列出每一跳 |
| **机场内部中转**（IPLC、IEPL、隧道转发） | 看不到具体经过几跳，但能判断**是否存在中转** | 入口与落地位置不同即说明有中转，例如入口在上海电信、落地在洛杉矶 |
| **落地位置真伪** | 能 | 对比两个信息：落地 IP 的 GeoIP 国家，以及 Cloudflare trace 的 `colo`（实际响应的机房）。IP 登记在美国、但 `colo` 为 HKG，说明服务器实际在香港，常称为「广播 IP」 |
| **落地→目标网站** | 不能 | 代理协议不转发 ICMP 和 TTL 信息，无法经代理做 traceroute |

### 用延迟做物理校验

光在光纤中每毫秒约走 200 km，因此往返时间存在下限：`最小 RTT ≈ 2 × 距离 ÷ 200 km/ms`。

| 校验 | 判断 |
| --- | --- |
| 经节点请求落地附近的 Cloudflare，总延迟**低于**你到声称落地城市的物理下限 | 落地位置不可信，例如上海到洛杉矶约 10,400 km，下限约 104 ms，实测只有 40 ms 则不可能在美国 |
| 你到入口的延迟很低（如 < 30 ms），总延迟接近你到落地城市的下限 | 典型的「国内入口 + 专线中转」 |
| 总延迟远高于下限 + 入口延迟 | 绕路或线路拥堵 |

### 结果标签

每个节点的出口信息增加「路径」一项，例如：

| 标签 | 条件 |
| --- | --- |
| 直连落地 | 入口与落地为同一 IP，或位于同一城市 |
| 经中转 · 上海 → 洛杉矶 | 入口与落地位于不同城市 |
| 链式代理 · 3 跳 | 来自客户端配置的 `relay` 或 `dialer-proxy` |
| ⚠ 位置存疑 | IP 归属国家与 `colo` 不符，或延迟低于物理下限 |

### 地图上的表现

```text
你 · 上海 ●┄┄┄┄○ 入口 · 上海电信 ════════════════○ 落地 · 洛杉矶
          虚线：你→入口              实线：机场内部线路（不知道具体途径，画为一段）
```

- 入口与你在同一城市时，入口点与「你」重合，只在列表中注明。
- 路由列表项增加一行：「经中转 · 入口 上海 电信 → 落地 洛杉矶」。
- 点击出口打开详情弹层：入口 IP / ASN、落地 IP / ASN、Cloudflare 机房、各段延迟和物理下限，以及结论。

### 隐私与成本

- 入口解析和 GeoIP、ASN 查询都在本机离线完成，不产生额外的网络请求。
- 实测仍然只访问 Cloudflare trace，与第 3.4 节的开关共用。
- `traceroute` 只在用户点击「检测线路」时执行。

## 5. 与「贴近系统原生」外观的关系

地图是全应用唯一的「视觉型」组件，但仍然遵守原生规范：陆地点阵用第三级灰，弧线用系统主题色和状态色，不使用渐变背景，深色模式自动适配。其他页面保持不变。

**已定：放在概览页**，替换原来的「当前出口」卡片，见原型 [prototype/index.html](prototype/index.html)。

- 布局：整宽卡片，左侧为地图，右侧 220 px 为路由列表（第一项为「当前出口」，其余为「其他路由」）；地图下方是「当前订阅」和「实时速度」两张并排的卡片。
- 路由来源：按活动连接的第一级代理组汇总，主代理组始终显示；全局模式下只显示 `GLOBAL`；直连模式和内核未启动时不画弧线，列表显示相应说明。
- 线是动态的，且每条路由一次只发一个请求：线从「你」逐渐画向出口，到达后淡出、出口泛起涟漪，停顿后再发下一个。流量越大停顿越短、线越粗；没有流量时不发送。开启「减少动态效果」时改为静态细线。具体参数见 design.md 5.1。
- 卡片右上角的「实测出口」按钮对当前所有出口做一次探测。
- 原型中的大陆轮廓是手绘的粗略多边形，正式版改为由 Natural Earth 生成。
